# AWG 외부 검증 (host/awg.py, host/run_awg_bbb.py, results/)

## 0. 검증 철학 — 왜 외부 크리스털 기준이 필요한가

보드가 자기 출력을 자기 입력으로 되받아 재는 **루프백(loopback, cmd 0x40)** 측정은 출력 타임스탬프 `t0`와 입력 타임스탬프 `t1`을 **같은 PRU 카운터, 같은 클럭 소스**로 찍는다. 이 카운터 자체가 "1틱 = 5 ns"라고 가정하고 있는 대상이므로, 그 카운터로 잰 결과가 "1틱이 정확히 5 ns"임을 증명하는 데 쓰이면 증명하려는 결론을 이미 전제로 깔고 있는 셈이 된다 — 전형적인 순환논증이다. 클럭이 실제로는 4.9 ns나 5.1 ns짜리였어도 루프백 측정은 여전히 "일관된" 숫자를 내놓기 때문에, 자기참조만으로는 절대 오차(진짜 5.000 ns인지)를 가려낼 수 없다. 이를 깨려면 보드의 PRU 클럭과 물리적으로 무관한, 그 자체로 크리스털에 트레이서블한 **독립 외부 기준**이 있어야 한다. 이 문서에서는 그 역할을 **Keysight 33521B AWG**의 `TRIG:DEL`(트리거→출력 지연, 4 ns 격자)이 맡는다. AWG가 독립적으로 알고 있는 지연값 τ와 보드가 측정한 값 M을 비교하면, 보드 클럭이 외부 기준 대비 실제로 몇 ns인지에 대해 순환 없는 증거를 얻을 수 있다.

## 1. 두 개의 독립적인 검증 축

AWG 검증은 성격이 다른 두 가지를 각각 검증한다. 이 둘을 섞어서 읽으면 안 된다.

### 1.1 축 A — 타임베이스 정확도 (펌웨어 cmd `0x42`)

**"자(尺)의 눈금 간격이 진짜 5.000 ns인가"**를 묻는 축이다.

측정 절차:
1. 보드가 `out0`(P8_11) 상승엣지로 AWG의 외부 트리거 입력을 쏜다.
2. AWG가 `TRIG:DEL = τ`(호스트가 지정, crystal-traceable, 4 ns 격자)만큼 기다렸다가 깨끗한 TTL 펄스 하나를 보드 입력(P8_16)으로 에코한다.
3. 보드는 트리거를 쏜 순간의 타임스탬프 `t0`와 에코가 도착한 순간의 타임스탬프 `t1`을 **`CT_ECAP.TSCTR`**(5 ns 틱, free-run)로 찍고 `M_ticks = t1 - t0`를 반환한다.
4. 호스트가 `M_ns = M_ticks × 5.0`을 계산한다.

여기서 핵심 관계식은 다음과 같다.

```
M_ns(측정값) = slope × τ(AWG 지연값) + intercept(고정 상수: AWG 트리거→출력 지연 + 케이블)
```

`intercept`는 τ와 무관한 고정 지연(AWG 내부 트리거 처리 지연, 케이블 전파 지연 등)이라 τ를 바꿔도 변하지 않는다. 반면 `slope`는 "τ가 1 ns 늘 때 M_ns가 몇 ns 느는가"이므로, 만약 보드가 가정하는 "1틱 = 5.000 ns"가 실제와 다르면(예: 실제 1틱이 5.1 ns라면) 같은 τ 증가분에 대해 M_ns가 더 빠르게 늘어나 `slope`가 1.000에서 벗어난다. 즉 **`slope`가 1.000에 가까울수록 PRU의 1틱이 정말 5.000 ns에 가깝다**는 뜻이고, `slope`가 1보다 크면 실제 틱이 5 ns보다 짧다는 뜻, 1보다 작으면 실제 틱이 5 ns보다 길다는 뜻이 된다. τ를 4 ns 격자로 여러 값 스윕하고 각 τ에서 여러 번 평균한 뒤 이 관계식에 선형적합(linear fit)을 하는 것이 축 A의 방법론이다.

### 1.2 축 B — 런타임 윈도우 위치 제어 (펌웨어 cmd `0x43`)

**"자가 정확하다고 해도, 원하는 그 눈금 위에 손가락(샘플링 시점)을 정확히 얹을 수 있는가"**를 묻는 축이다. 축 A와는 다른 종류의 오차 원천(정확도가 아니라 *제어성*·*위치잡기 정밀도*)을 검증한다.

측정 절차:
1. 보드가 `out0` 상승엣지로 AWG를 트리거한다(축 A와 동일한 트리거 경로).
2. 이번에는 카운터를 스핀(spin)하며 값을 읽는 방식이 아니라, `pru_delay.asm`의 **하드웨어 `loop` 명령**으로 정확히 `D` 사이클(`D × 5 ns`)만큼 지연한다.
3. 지연이 끝난 그 순간, 입력 핀을 **단 한 번** 샘플링해서 `bit`(0 또는 1)를 얻는다 — 스핀 폴링이 아니라 단발 스트로브(strobe)다.
4. 호스트가 `D`를 스윕하면서, 샘플 결과가 0에서 1로 바뀌는 경계점 `D*`(50% 크로싱, 반복 평균으로 결정)를 찾는다.
5. AWG의 τ 값을 바꿔가며 이 `D*`(→ ns 단위 `window_pos_ns`)가 τ의 변화량만큼 정확히 따라 움직이는지 다시 선형적합한다.

`slope`가 1.0000에 가깝다는 것은, "윈도우(샘플링 시점)를 표적 지점으로 옮기라"는 요청(τ 변화)이 실제로 그만큼 정확하게 반영된다는 뜻 — 즉 **런타임 윈도우 위치 제어가 5 ns 단위로 정확하다**는 증거다.

### 1.3 왜 두 축이 다른가 (대비)

축 A는 "카운터 1틱이 몇 ns인가"라는 **정확도(accuracy)** 문제이고, 축 B는 "그 카운터 위에서 원하는 지점에 정확히 도달했는가"라는 **제어성/포지셔닝(positioning)** 문제다. 자의 눈금 간격이 정확해도(축 A), 손가락(측정 메커니즘)이 떨리면(축 B) 원하는 눈금에 못 앉는다. 실제로 이 프로젝트에서는 축 A의 정확도(slope 0.99986)는 그대로인 채로, 축 B의 지연 메커니즘을 spin-read 루프(`CT_ECAP.TSCTR`을 읽어 목표 틱과 비교하는 방식, cmd `0x41`)에서 zero-overhead HW `loop` 명령(cmd `0x43`)으로 바꾸자 잔차가 크게 개선된 사례가 있다 — 두 축이 서로 독립적인 실패 모드를 가진다는 직접적 증거다(자세한 수치는 5장 참고).

## 2. awg.py — SCPI로 AWG를 실제로 무엇을 설정하는가

`awg.py`의 `Awg33521B` 클래스는 소켓으로 `192.168.0.4:5025`(SCPI raw TCP, 기본값)에 접속하고, `pyvisa` 없이 직접 SCPI 문자열을 주고받는다. AWG의 역할은 코드 주석 그대로 **"TRIGGERED, PROGRAMMABLE-DELAY ECHO"**다.

`configure_echo(width_ns=200, high_v=3.3, low_v=0.0, slope="POS")`가 순서대로 보내는 SCPI 명령:

| SCPI 명령 | 값 | 의미 (코드 주석 그대로) |
|---|---|---|
| `*CLS` | — | 상태/에러 큐 클리어 |
| `FUNC PULS` | — | 펄스 함수 선택 |
| `OUTP:LOAD INF` | 무한대(hi-Z) | 보드 입력이 hi-Z이므로 이 설정이어야 **표시 전압 = 실제 전달 전압** |
| `VOLT:HIGH %g` | `high_v`(기본 3.3 V) | 에코 하이레벨 |
| `VOLT:LOW %g` | `low_v`(기본 0.0 V) | 에코 로우레벨 |
| `FUNC:PULS:TRAN:BOTH MIN` | 최소 | 가장 빠른 엣지(코드 주석: **~8.4 ns**) |
| `FUNC:PULS:WIDT %.10f` | `width_ns × 1e-9`(기본 200 ns) | 에코 펄스 폭 — 상승엣지만 타이밍에 중요하고, 폭은 보드 입력이 깨끗이 인식할 정도로만 넓으면 됨("flat-top TTL") |
| `FREQ 1000` | 1 kHz | 캐리어 주기 기준값. `BURS:NCYC 1`이라 트리거당 펄스 1개만 나가므로 이 값 자체는 실질적 의미가 크지 않음 |
| `BURS:MODE TRIG` | — | 트리거 버스트 모드 |
| `BURS:NCYC 1` | 1 | 트리거 1회당 정확히 1펄스 |
| `TRIG:SOUR EXT` | — | 트리거 소스 = 외부(보드가 트리거를 구동) |
| `TRIG:SLOP %s` | `slope`(기본 `POS`) | 트리거 엣지 극성 |
| `TRIG:DEL 0` | 0 | 트리거→에코 지연 초기화(이후 호스트가 스윕) |
| `BURS:STAT ON` | — | 버스트 모드 활성화 |

각 명령 사이 `time.sleep(0.02)`, 전체 전송 후 `*WAI`(이전 명령 완료 대기) + `sleep(0.1)`, 마지막에 `check_error()`(`SYST:ERR?` 조회, 에러 코드가 0이 아니면 `RuntimeError`)로 마무리한다.

그 외 주요 메서드:

| 메서드 | 역할 |
|---|---|
| `idn()` | `*IDN?` — 장비 식별 |
| `set_delay_ns(tau_ns)` | `TRIG:DEL %.10f`(τ×1e-9) 설정 + `*WAI` + `sleep(0.005)`. **33521B 격자는 4 ns**이므로 `tau_ns`는 4의 배수로 맞춰 쓴다 |
| `output(on)` | `OUTP 1/0` + `sleep(0.02)` + `check_error()` |
| `armed()` | `STAT:OPER:COND?`의 **비트 5(값 32)** — "Waiting for Trigger" 상태 조회 |
| `triggers_arriving(secs)` | `STAT:OPER:PTR/NTR 65535`로 전이 래치 설정 후 일정 시간 `STAT:OPER:COND?`를 폴링해 실제로 외부 트리거가 들어오는지 확인하는 배선 점검용 진단 메서드(메인 스크립트가 아니라 `awg.py` 자체 `__main__` 블록에서 쓰임) |
| `check_error()` | `SYST:ERR?` — 0이 아니면 예외 |

## 3. run_awg_bbb.py — 알고리즘

`run_awg_bbb.py`는 **축 A(타임베이스 정확도, cmd `0x42`)** 스윕을 수행하는 스크립트다. BBB가 `192.168.0.x` LAN에 있어 SCPI 제어(AWG)와 PRU 측정(`/dev/rpmsg0`)을 한 프로세스에서 동시에 수행한다(BeagleY-AI처럼 split 배포가 필요 없음).

### 3.1 환경변수 (코드 기본값 그대로)

| 변수 | 기본값 | 의미 |
|---|---|---|
| `AWG_IP` | `192.168.0.7` | AWG IP |
| `TAU_START` | `0` (ns) | 스윕 시작 지연 |
| `TAU_STOP` | `1000` (ns) | 스윕 종료 지연 |
| `TAU_STEP` | `4` (ns) | AWG의 4 ns 격자 — "**5 ns LSB보다 미세해서 계단(staircase)을 드러낸다**" (코드 주석) |
| `N_SAMP` | `5` | τ당 단발(single-shot) 반복 횟수(중앙값 기반) |
| `REARM_S` | `0.006` (6 ms) | 단발 사이 간격 — AWG가 재무장(re-arm)할 시간 |
| `TICK_NS` | `5.0` (상수, env 아님) | 틱→ns 환산 계수 |
| `ECHO_MIN_NS` / `ECHO_MAX_NS` | `20.0` / `4000.0` | 그럴듯한 AWG 에코 윈도우 — 이 범위 밖 값은 스퓨리어스로 간주해 적합에서 제외 |

> ⚠️ 코드 기본값은 `N_SAMP=5`이지만, 아래 5장에 기록된 실제 검증 실행(251점, 잔차 3.2 ns)은 **`N_SAMP=40`으로 환경변수를 오버라이드**해 수행된 것이다. 스크립트 자체의 기본값과 실제 보고된 결과의 평균 횟수가 다르므로 재현 시 `N_SAMP=40`을 명시해야 한다.

### 3.2 측정 루프

1. `Awg33521B(AWG_IP)` 연결 → `idn()` 출력 → `configure_echo(width_ns=200)`(2장의 SCPI 설정) → `output(True)` → `armed()`/`check_error()` 확인.
2. `/dev/rpmsg0`를 `O_RDWR`로 오픈.
3. `tau`를 `TAU_START`부터 `TAU_STOP`까지 `TAU_STEP` 간격으로 증가시키며 반복:
   - `awg.set_delay_ns(tau)`로 `TRIG:DEL=tau` 설정.
   - `tau % 200 == 0`일 때만 `check_error()`(매 스텝 확인은 느려서 주기적으로만 확인).
   - `measure_tau(fd)` 호출:
     - `N_SAMP`회 반복하여 `awgshot1(fd)` 호출. 이 함수는 `[0x42][n=1:4]`(5바이트)를 `/dev/rpmsg0`에 쓰고, `select()`로 최대 5초 응답을 기다린 뒤 22바이트 응답을 파싱해 `ngood==1`일 때만(=단발 성공) 그 값(`mn`, 틱 단위)을 반환한다.
     - 매 단발 사이 `REARM_S`(6 ms)만큼 대기한다 — **AWG가 ms 단위로만 재무장하기 때문에, 펌웨어 내부에서 `n>1`짜리 버스트를 한 번에 요청하면 대부분의 샷을 놓친다.** 그래서 호스트가 단발(n=1)을 쏘고 매번 SCPI 왕복 사이 간격(6 ms)을 직접 넣어 AWG가 재무장할 시간을 벌어준다.
     - 수집된 값들을 정렬해 중앙값을 구하고, 중앙값에서 **±3틱** 벗어난 값(엉뚱한 엣지를 잡은 outlier)을 버린 뒤 남은 값들의 평균(fractional 틱)을 취한다.
   - `m_ns = mean × TICK_NS`(5.0)로 환산.
   - `ECHO_MIN_NS < m_ns < ECHO_MAX_NS` 범위 안일 때만 그 점을 회귀용 리스트(`taus`, `means`)에 추가.
4. 스윕이 끝나면 `fd`/AWG 소켓을 닫는다.

### 3.3 선형회귀와 판정 기준

```python
def linfit(xs, ys):
    n = len(xs); sx = sum(xs); sy = sum(ys)
    sxx = sum(x * x for x in xs); sxy = sum(x * y for x, y in zip(xs, ys))
    slope = (n * sxy - sx * sy) / (n * sxx - sx * sx)
    inter = (sy - slope * sx) / n
    rms = math.sqrt(sum((y - (slope * x + inter)) ** 2 for x, y in zip(xs, ys)) / n)
    return slope, inter, rms
```

표준 OLS(최소제곱) 공식으로 `slope`, `inter`(절편), 잔차 RMS를 계산한다. 통과 판정은 스크립트 자체 출력 문구 기준 `abs(slope - 1.0) <= 0.03`(코드: `ok = abs(slope - 1.0) <= 0.03`)이며, 통과 시 `"PASS - 5 ns output<->input resolution verified vs external AWG"`, 실패 시 `"CHECK - inspect staircase / wiring"`를 출력한다.

> ⚠️ 판정 허용치 표기가 두 곳에서 다르다: `run_awg_bbb.py`의 출력 문자열은 **"PASS if ~1.000 +/- 0.03"**인 반면, 아래 5장의 실제 결과표는 **"PASS 기준 1.000 ± 0.02"**로 적고 있다. 실측 슬로프(0.99986)는 둘 중 어느 기준으로도 통과한다.

마지막으로 CSV를 `/home/xilinx/pru/awg_staircase.csv`에 `tau_ns,M_ns` 헤더로 기록한다(`results/awg_staircase_avg.csv`는 이 형식과 동일한 컬럼 구조를 가진, N=40 평균 실행의 산출물이다).

| `window_pos_ns` | 그 τ에서 cmd `0x43`의 `D`를 스윕해 찾은 0→1 전이 경계점 `D*`를 ns로 환산한 값(50% 크로싱, N=40 평균) |

`tau_ns`는 0부터 480까지 40 ns 간격, 총 **13행**이다.

> ⚠️ 이 CSV를 생성하는 축 B 전용 호스트 스크립트([OPERATIONS.md](OPERATIONS.md)에 있는 `scripts/verify_window.sh` 계열)는 이번에 정독한 파일 목록(`host/awg.py`, `host/run_awg_bbb.py`)에 포함되어 있지 않다. `run_awg_bbb.py`는 cmd `0x42`만 전송하므로 **`awg_strobe_avg.csv`를 만드는 스윕 루프 자체의 소스 코드는 이 문서가 직접 확인하지 못했다** — 위 컬럼 설명은 이전 검증 기록의 방법론 서술과 CSV 실제 값(4장 표)을 근거로 한 것이다.

## 5. 실측 결과 (반올림 없음)

| 축 | 점 수 | 평균화 | 기울기 | 절편 | 잔차 RMS | 비고 |
|---|---|---|---|---|---|---|
| **A. 타임베이스 정확도** (cmd `0x42`) | 251 | τ당 N=40 | **0.99986** | **257.6 ns** | **3.2 ns** | 단발(n=1) 잔차는 7.3 ns; PRU 틱 = 5.000 ns ±0.014% |
| **B. 런타임 윈도우 포지셔닝** (cmd `0x43`, HW-LOOP) | 13 | N=40(0→1 전이 50% 크로싱) | **1.0000** | — (원 데이터에 절편 값 미기재) | **0.16 ns** | eCAP-spin(cmd `0x41`) 방식은 잔차 8 ns 워블이었음 |

다시 말해: 축 A의 기울기 1.000은 "자기참조가 아니라" AWG 외부 크리스털 기준 스윕에서 나온 값이므로 "자(尺)의 눈금 간격이 5.000 ns로 정확하다"는 **타임베이스 정확도** 증명이고, 축 B의 잔차 0.16 ns는 "그 눈금 중 원하는 하나에 손가락을 정확히 얹을 수 있다"는 **포지셔닝** 증명이다.

내부 cross-check로만 인용되는 루프백(cmd `0x40`, v1.7에서 제거됨) 수치도 참고용으로 함께 기록되어 있다: 시행/검출성공/타임아웃 = 1000/1000/0, 출력→입력 루프 지연 = 19 IEP tick = 95.0 ns, 지터(max−min) = 0.0 ns. 이 값은 "내부/자기참조 — 5 ns 증명 단독 불가, cross-check 전용"으로 명시되어 있다.

## 6. 정직한 한계

> ⚠️ **AM335x BeagleBone Black 헤더에는 PRU eCAP의 하드웨어 캡처 입력 핀(capin)이 물리적으로 배선되어 있지 않다.** 이는 (v1.7에서 제거된) 진단 명령 `0x50`으로 확인됐던 사실이며(`CEVT1=0`), K3/AM64x 계열 주소공간(`0x11Cxxx`)에만 해당 핀이 존재하고 AM335x(`0x44E108xx`)에는 없다. 그 결과 **입력 엣지 검출은 eCAP의 하드웨어 엣지 래치가 아니라, `CT_ECAP.TSCTR`(자유주행 카운터)을 기준으로 `R31` GPI 비트를 소프트웨어가 폴링해서 엣지 도착 순간을 근사하는 방식**이다(`main.c`의 cmd `0x42` "tight echo poll" 4배 언롤 루프 참고 — [FIRMWARE.md](FIRMWARE.md) §7.3).

이 소프트웨어 폴링 구조 때문에 단발(single-shot) 측정에는 폴링 루프의 그랜율래리티만큼 지터가 남는다 — 실제로 축 A의 단발(n=1) 잔차는 **7.3 ns**였다. 이는 5 ns 틱 하나보다 큰 값으로, 단일 샷만으로는 "5 ns 분해능"을 주장하기에 부족하다는 뜻이다. 그래서 τ(또는 D)마다 **여러 번(N=40) 반복해 평균**하는 절차가 필요했고, 평균화 후에야 축 A 잔차가 sub-LSB 수준인 **3.2 ns**로, 축 B 잔차가 **0.16 ns**로 떨어졌다. 즉 이 검증 방법론 전체가 "단발 SW-poll의 지터를 반복 평균으로 통계적으로 눌러서 5 ns 주장을 뒷받침한다"는 구조이며, capin 미배선이라는 하드웨어 제약이 근본 원인이라는 점은 숨기지 않고 밝혀 둔다.

그 외 함께 남는 제약(코드/문서에서 확인된 것만):
- AWG(33500B 계열)는 ms급 재무장이 필요해, 펌웨어 내부에서 `n>1`짜리 배치 샷을 요청하면 대부분 놓친다 — 호스트가 단발 + `REARM_S`(6 ms) 간격으로 우회한다(`run_awg_bbb.py` 주석).
- cmd `0x42`의 tight echo poll은 `guard < 16000u` 사이클 안에 에코를 못 찾으면 타임아웃(`ntmo` 카운트) 처리한다(`main.c`).

## 7. cmd `0x42` / `0x43` 요청·응답 payload 포맷 (firmware/main.c 확인)

두 명령 모두 `REQUIRE_LEN(5)` 체크가 있어 요청은 최소 5바이트(`cmd` 1바이트 + 4바이트 파라미터)여야 하며, 짧으면 `[cmd][0xEF]`(NAK) 2바이트를 돌려주고 그 케이스를 즉시 빠져나온다.

### cmd `0x42` — AWG-SHOT (타임베이스 정확도)

**요청**

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| 0 | 1 | `cmd` | `0x42` |
| 1–4 | 4 (LE uint32) | `n` | 요청 샷 수. `n==0` 또는 `n>2000`이면 펌웨어가 내부적으로 `n=100`으로 대체. `run_awg_bbb.py`는 항상 `n=1`을 보낸다 |

**응답 (총 22바이트)**

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| 0 | 1 | `cmd` | `0x42` (에코) |
| 1 | 1 | `ok` | `ngood>0`이면 1, 아니면 0 |
| 2–5 | 4 (LE uint32) | `ngood` | 타임아웃 없이 성공한 샷 수 |
| 6–9 | 4 (LE uint32) | `ntmo` | 타임아웃된 샷 수 |
| 10–13 | 4 (LE uint32) | `min` | 성공한 샷들 중 최소 간격(eCAP 틱, 5 ns/틱) |
| 14–17 | 4 (LE uint32) | `max` | 최대 간격(틱) |
| 18–21 | 4 (LE uint32) | `sum` | 간격 합(틱). 평균 = `sum / ngood` |

`n=1`(단발)일 때는 `ngood`가 0 또는 1이고, 성공 시 `min == max == sum`이므로 그 값 자체가 그 1회 측정치(틱)다 — `run_awg_bbb.py`의 `awgshot1()`이 `mn`을 그대로 반환하는 이유다.

### cmd `0x43` — AWG 윈도우 스트로브 (런타임 윈도우 포지셔닝, HW-LOOP)

**요청**

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| 0 | 1 | `cmd` | `0x43` |
| 1–4 | 4 (LE uint32) | `D` | 출력 후 대기할 PRU 사이클 수(`D×5 ns`). `D>4000`이면 펌웨어가 `4000`으로 클램프 |

**응답 (총 7바이트)**

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| 0 | 1 | `cmd` | `0x43` (에코) |
| 1 | 1 | `ok` | 항상 1 (타임아웃 경로 없음) |
| 2 | 1 | `bit` | 출력 상승엣지 + `D×5 ns` 시점에 샘플링한 `R31` `IN0` 비트(0 또는 1) |
| 3–6 | 4 (LE uint32) | `D` | 요청받은 `D`를 그대로 에코 |

호스트는 고정 τ에서 `D`를 스윕하며 `bit`가 0→1로 바뀌는 경계 `D*`를 찾고(반복 평균으로 50% 크로싱을 특정), τ를 바꿔가며 이 `D*`가 τ만큼 정확히 이동하는지를 5장의 회귀로 확인한다.
