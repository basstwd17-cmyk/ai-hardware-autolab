# 다른 보드 등록과 개발

기준일: 2026-10-01

보드·장비 구성을 등록한 뒤 작업마다 선택한다. 모든 보드는 같은
Lead → Builder → Verifier 흐름을 사용한다. 새 보드를 추가하기 위해 에이전트 팀,
실행 계약, Gate, Campaign 또는 승인 절차를 만들지 않는다.

## 현재 가능한 것

| 대상 | 현재 지원 |
|---|---|
| 기존 RTASE 구성 | BBB/PRU, MachXO2 SRAM, JTAG, RTM3004 도구 유지 |
| 연결하지 않은 새 보드 | 모델·리비전, 소스 경로·문서·메모 등록 후 소스 개발·빌드 |
| USB 장치 | Windows PnP 탐색, 선택 등록, 현재 OS 존재 확인 |
| 시리얼 보드 | COM 탐색 또는 직접 지정, 연결 확인, 바이트 송수신 |
| 새 보드 + 기존 스코프 | 등록된 RTM3004 주소·입력 설정 재사용, 사용자 지정 채널로 측정 |
| 새 보드 펌웨어 업로드 | 해당 프로그래머 실행기를 추가해야 함. USB가 보인다고 업로드 도구가 생기지 않음 |

시리얼 통신은 8N1이며 baudrate, 송신 hex, 읽을 최대 바이트 수와 timeout을 지정한다.
일부 보드는 포트를 여는 것만으로 리셋될 수 있다. 에이전트는 보드 문서를 바탕으로
프로토콜을 선택하고, 실제 송수신 값으로 결과를 판단한다. 송신 성공이나 빈 응답만으로
원하는 펌웨어 기능이 완성되었다고 판단하지 않는다.

## 사용 순서

1. 시작 화면의 **이번 작업의 보드·장비 구성**에서 기존 구성을 고르거나
   **다른 보드 등록**을 펼친다.
2. 구성 이름, 실제 보드 모델, 저장 ID와 구성 리비전을 입력한다.
   소스 경로는 C:\KIST 기준 상대 경로를 한 줄에 하나씩 입력한다.
   해당 소스는 작업공간에 포함될 일반 프로젝트 소스여야 한다. 문서 URL과 개발 환경 메모도 추가할 수 있다.
3. 필요하면 **연결된 USB·시리얼 장치 찾기**를 누르고 사용할 연결만 선택한다.
   목록은 OS가 제공하는 포트·VID/PID·설명·장치 식별 정보이다. 카메라나 저장장치 같은
   일반 주변장치도 보일 수 있다. 목록의 이름을 보드 모델로 자동 확정하지 않는다.
   연결 없이 등록하거나 COM4처럼 포트를 직접 입력할 수도 있다.
4. 계측이 필요하면 **함께 사용할 기존 스코프**를 선택한다.
   주소·종단·프로브·전압 한계는 재사용하지만 기존 보드의 신호명·핀은 복사하지 않는다.
5. **구성 등록하고 선택**을 누른 뒤 시나리오를 제출한다.
   예: “선택한 보드의 UART 상태 조회 프로토콜을 문서에서 찾아 응답을 확인해줘.”
   스코프를 쓸 때는 “CH1=PWM”처럼 실제 연결을 시나리오에 포함한다.

등록·선택을 위해 데몬을 재시작할 필요는 없다. 최근 선택은 브라우저에 기억한다.
사용자는 새 작업을 시작할 때 모델 선택도 함께 적용할 수 있다.

연결 탐색과 확인은 선택사항이다. 작업 시작 시 전체 장비를 검사하지 않는다.
Lead·Builder·Verifier가 필요한 장비 ID만 check_connections에 전달하며,
같은 job의 기존 관측·시각·run은 다음 역할과 재개된 작업에서 재사용한다.
새 관측이 필요할 때 해당 장비만 다시 확인한다.

## 작업과 장비의 연결 방식

- 등록: `boards/<board_id>/<revision>/hardware.yaml`에 저장한다.
  새 등록은 schema_version 2이며 연결 정보와 개발 자료를 담는다.
  기존 RTASE schema_version 1도 계속 읽는다.
- 선택: hardwareSelection = {board_id, revision}을 mission 요청에 포함한다.
  선택한 구성·해시, 사용 가능한 도구, 보드 소스·문서를 job의 최초 기록에 저장한다.
- 실행: SelectedHardwareExecutor가 job에 저장된 구성을 읽어 도구를 실행한다.
  다른 작업의 선택값이나 브라우저 설정을 실행 대상으로 사용하지 않는다.
- 공유 장비: 서로 다른 구성에서 같은 스코프를 사용해도 하나의 실행 잠금으로
  직렬화한다. 실행을 기다리는 동안 취소된 작업은 장비를 호출하지 않는다.
- 변경: 이미 등록된 ID/리비전에 다른 내용을 덮어쓰지 않는다. 구성 변경은 새 리비전으로
  등록한다. 호스트에서 파일을 직접 바꾼 경우 기존 job은 변경된 장비로 자동 이동하지 않는다.
- 자료: inputs.selected_board로 보드별 소스 경로·문서·메모를 전달한다.
  지식 검색도 job의 보드/리비전으로 범위를 정한다. 작업공간에 RTASE 소스가 존재해도
  다른 보드의 사실이나 배선으로 사용하지 않는다.

데몬의 기본 구성은 --hardware-board와 --hardware-revision으로 정한다.
--knowledge-hardware/--knowledge-revision은 실제 장비 선택과 분리되어 있다.
CLI에서는 mission의 `--board <등록된 ID> --revision <등록된 리비전>`으로 개별 작업의
구성을 지정한다. 예: mission '선택한 보드 소스의 구조를 설명해줘' --board my-board --revision v1.0

현재 이 등록·탐색 UI는 로컬 웹 서버에서 사용한다. 운영 반영 시 데몬과 웹 서버를 재시작하고
새 프론트엔드 빌드를 사용한다. 기존 별도 휴대폰 릴레이 화면은 이 등록 UI를 제공하지 않는다.

## 연결 관측과 실제 기능은 구분한다

- USB/COM present: 선택한 연결이 OS 목록에 존재한다. 보드 모델·펌웨어·배선은 미검증이다.
- 기존 식별 드라이버의 connected: 실제 BBB 모델, 스코프 식별 응답 또는 JTAG 체인이 일치한다.
  이 결과도 배선이나 출력 기능의 검증은 아니다.
- serial_exchange run: 실제 송수신 바이트, 설정과 오류를 기록한다.
  확인된 USB 식별자가 달라졌으면 같은 COM 번호의 다른 장치를 대신 사용하지 않는다.
- measure_scope run: 시나리오에 선언한 새 보드의 신호·채널로 측정한다.
  입력 종단·프로브·전압 한계는 계속 검사한다. 소프트웨어가 프로브를 옮겼다고 표시하지 않는다.

새 보드에는 RTASE의 BBB 접속 정보, SPI 핀, CPLD SRAM 전용 조건을 복사하지 않는다.
기존 스코프 드라이버 내부의 Contracts/SafetyGate는 물리 설정을 전달하는 호환 계층으로
남아 있다. 새 보드 등록·시리얼 실행에는 실행 계약 생성이나 승인을 추가하지 않았다.

## 구현 위치와 인계 시 확인할 것

| 파일 | 역할 |
|---|---|
| boards/discovery.py | 포트를 열지 않는 USB/COM 탐색과 연결 정보 비교 |
| boards/registry.py | 구성 목록, 등록·재사용, 보드 자료 저장 |
| boards/hardware.py | 구성 읽기와 공개 장비 설명, 기존 드라이버 호환 |
| boards/connections.py | 에이전트가 선택한 장치만 확인하고 결과 보관 |
| hwtools/local_board.py | 새 보드의 연결 관측·시리얼 실행·run 기록 |
| orchestrator/conversation_hardware.py | job별 구성 라우팅, 제공할 도구와 장비 호출 |
| webui/frontend/src/app/HardwareSetups.tsx | 선택·탐색·등록 화면 |
| tests/test_hardware_registry.py | 등록, HTTP, 작업별 라우팅, 스코프 재사용과 세 역할 통합 검증 |

새 보드의 전체 자동 개발을 검증하려면 그 보드용 프로그래머 실행기와 실제 연결 장비가
추가로 필요하다. 예를 들어 STM32 업로드는 프로그래머 선택, 장치 식별, 펌웨어 경로·쓰기
주소, 결과 기록을 처리하는 도구를 별도로 연결해야 한다. 이는 새 계약 엔진이 아니라
해당 연결 방식의 도구 구현이다. 범용 SSH 업로드·실행과 임의 계측기 드라이버도 아직 없다.

2026-10-01에는 실제 Windows USB 목록 조회를 확인했고, 보드 통신과 스코프 측정 경계는
모의 장비로 검증했다. 실제 모델과 새 실물 보드를 함께 사용한 개발→업로드→파형 검증은
완료하지 않았다. 정확한 테스트 결과는 STATUS.md에 유지한다.
