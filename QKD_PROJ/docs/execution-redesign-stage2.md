# 실행부 교체 — 2단계: 최소 대화 실행 코어

작성일: 2026-09-10. **오프라인 테스트 전용 구현이며 웹의 기본 실행 경로는 아직 바꾸지 않았다.**

사용자가 원하는 기능을 제시하면 에이전트가 조사·설계·개발 방법을 선택하고,
실제 결과를 검토해 수정하는 것이 목표다. 보드별 고정 절차나 에이전트가 작성해야 할
실행용 계약을 새로 추가하지 않았다. 실제 모델·장비 연결은 다음 단계다.

## 구현

`orchestrator/conversation_flow.py`의 `ConversationFlow`:

`Lead → Builder → Verifier → 완료 또는 Builder/Lead로 수정 요청`

- Lead는 일반 문장으로 목표의 해석, 접근 방법, 참고 자료와 주의사항을 전달한다.
- Builder는 코드와 결과 파일을 전달한다. 계약 컴파일러나 prepared_plan을 호출하지 않는다.
- Verifier는 원래 요청과 결과를 비교하고, 구체적인 수정 사유와 대상 역할을 반환한다.
- 플랫폼은 역할 순서, 원장 기록, 피드백, 취소, 산출물 경로/해시를 관리한다.
- 에이전트 응답에 넣은 가짜 role·authority·next_phase 값으로 플랫폼 상태를 바꿀 수 없다.

응답은 최소한의 전달 봉투만 사용한다. 일반 문장은 `summary`에 들어가며,
도구별 인자나 핀 매핑·전기 조건·완성된 YAML은 역할 전달의 필수조건이 아니다.

```json
{"status": "ready", "summary": "기존 코드를 활용해 구현했습니다.", "artifacts": ["result.txt"]}
```

```json
{"status": "revise", "target": "builder", "summary": "바이트 순서가 반대입니다. 기존 결과를 보존하고 수정해주세요."}
```

Lead/Builder는 ready·revise·needs_user, Verifier는 satisfied·revise·needs_user를 쓴다.
최종 응답 형식 교정과 실제 실행 오류의 문맥 내 복구는 3단계 런타임 어댑터에서 연결한다.
현재 프로토타입은 잘못된 응답 때문에 이전 동작 전체를 자동 재실행하지 않는다.

## 기록과 재개

기존 JobLedger와 SQLite 스키마를 그대로 쓴다. 새 Brief의 workflow는
`conversation-prototype-v1`, 실행 모드는 offline이다. 기존 job은 자동 편입하지 않는다.
DB의 기존 필수 gate 필드에는 내부 식별자만 넣으며 계약 파일을 조회하지 않는다.

- `advance()` 한 번에 모델 대용 runtime 한 번 이하 호출.
- `conversation.turn.started/completed/failed`와 `conversation.feedback`로 다음 역할 파생.
- 원래 목표, 역할별 최신 메시지, 사용자 피드백, 산출물 목록과 전체 원장 참조를 전달.
- Verifier 판정 중 새 피드백이 오면 낡은 판정으로 끝내지 않고 Lead로 전달.
- 답변 대기는 답변 후 Lead로 돌아간다. 사람 피드백의 actor는 human으로 기록.
- 완료 응답을 기록한 뒤 프로세스가 사라져도 다음 호출에서 모델 재실행 없이 완료 처리.
- 시작만 기록된 불명확한 시도는 중복 실행하지 않는다. 취소한 job은 재개하지 않는다.
- 테스트용 기본 모델 턴 상한은 12이며 생성 시 설정 가능하다. 도달하면 미완료로 남긴다.

한 소유자가 호출을 직렬화한다는 전제다. 동시 실행·실행 중 취소 인터럽트·운영 데몬의
재시작 복구와 연결했다고 주장하지 않는다. 새 이벤트를 웹에 표시하는 연결도 아직 없다.

## 결과의 의미

Verifier의 satisfied에는 작업공간 안에 존재하며 이전에 전달된 해시와 같은 결과 파일이
필요하다. 누락·경로 탈출·변조된 파일이나 Builder의 성공 선언만으로 완료하지 않는다.
**파일 존재와 해시는 기능 성공을 증명하지 않는다.** 현재 테스트는 전달과 상태 전이만
검증한다. 실제 하드웨어 성공 여부는 이후 실제 run·측정값과 요구사항 검토로 확인해야 한다.

runtime은 오프라인 callable이다. `hardware_access: false`는 문맥 표시일 뿐 OS 샌드박스가
아니다. 임의 callable을 장비 안전 격리 수단으로 사용하면 안 된다. 작업공간도 테스트가
만든 폴더를 받으며 실제 WorkspaceManager 생성·권한 적용은 다음 연결 작업이다.

## 검증

결과: 새 코어 18개 + 기존 기준선 회귀 합계 **175 passed, 1 skipped**.
전체 저장소 테스트나 실제 모델·하드웨어 검증 결과가 아니다.

새 실행부 18개 사례: 정상 역할 전달, Builder/Lead 수정 루프, 원인/기존 결과 유지,
중간 피드백, 질문/답변, 런타임 중단·형식 오류의 중복 실행 방지, 취소 우선,
완료 직전 크래시 재개, 증거 누락·변조·경로 탈출, 턴 예산, 기존/hardware job 거부.

기존 1단계 기준선 소스 7개 SHA-256은 그대로 유지했다. 운영 job·장비·기존 산출물,
원장 스키마, 기본 라우터와 웹은 변경하지 않았다. 프런트엔드 빌드/배포는 필요 없다.

```powershell
py -3 -m pytest QKD_PROJ/tests/test_conversation_flow.py -q --tb=short -p no:cacheprovider
```

다음 3단계는 실제 Codex runtime을 이 작은 봉투에 연결하고, Builder의 코드 작성·명령
실행·일반 오류 수정을 같은 작업 문맥에서 이어가게 하는 것이다. 장비 실행/권한/run 연결과
실물 시나리오 검증을 거친 뒤에만 기본 라우팅을 전환한다.
