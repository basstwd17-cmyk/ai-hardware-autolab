# 시나리오 중심 실행 단순화 — 2026-09-10

## 목표

사용자가 시나리오를 제시하면 에이전트가 방법을 선택하고 구현·실행·검토·수정을 이어간다.
플랫폼은 구현 방법을 계약 문서로 다시 제출하게 하지 않고, 대화·작업공간·도구·실제 결과를 연결한다.

## 처음부터 만든다면

필요한 구성은 역할 실행기 하나, 작업별 공유 작업공간 하나, 작업 기록 하나, 도구 연결부 하나다.
Lead/Builder/Verifier는 같은 실행기에 다른 역할 지침을 주는 세 역할이다.
별도 계약 작성 에이전트나 다단계 승인 그래프는 기본 구성에 넣지 않는다.

1. 사용자 시나리오와 현재 소스·장비 정보를 작업에 저장한다.
2. Lead가 목표·접근 방법·필요한 참고 자료를 일반 문장으로 Builder에게 전달한다.
3. Builder가 같은 작업공간에서 도구를 사용해 구현하고 일반 오류를 직접 고친다.
4. Verifier가 원래 요청·사용자 피드백·코드·실제 실행 결과를 비교한다.
5. 구현 문제가 남으면 Builder, 접근 방법이 틀렸으면 Lead로 직접 돌려보낸다.
6. 사용자만 아는 정보가 필요하면 질문하고, 답변 후 같은 작업을 이어간다.
7. 요청을 충족하면 결과와 변경 파일을 전달한다. 프로세스 중단이나 예산 소진은 완료가 아니다.

검증에 필요한 실행은 Builder에게 요청할 수 있다. Verifier 역할 자체에 무조건 별도 빌드나
측정 실행을 강제하지 않는다. 조사·설명만 요청한 경우 가짜 결과 파일도 요구하지 않는다.

## 실제 코드와 비교

현재는 기존 autonomous-v1 경로와 conversation-prototype-v1 경로가 함께 존재한다.
9월 10일 초기 stage3 문서보다 웹 연결 소스가 더 진행되어 있다. 아래는 소스 기준이며
운영 데몬에 적용되었다거나 실제 장비 검증이 끝났다는 의미가 아니다.

| 항목 | 기존 경로 | 현재 새 코어 / 목표 |
| --- | --- | --- |
| 작업 시작 | 사전 검사, 자료·보드·계약 준비와 기존 mission 생성 | 웹의 명시적 Offline 요청은 새 코어로 제출하는 연결이 있음 |
| 역할 전달 | Plan, 준비 작업, prepared_plan, 실행 결과 변환 | 일반 문장 + 상태 + 선택적 파일 참조 |
| 구현 방법 | 모델이 정한 계획을 플랫폼 단계·계약 형식으로 해석 | Builder가 작업 중 방법과 도구 사용을 결정 |
| 계약 | 일반 개발 계약은 이미 제거됐으나 장비 단계의 컴파일·바인딩은 남음 | 개발 대화에서는 계약 컴파일 호출 없음; 장비 연결부는 후속 이관 필요 |
| 수정 루프 | 단계별 준비·형식 교정·재계획 경로 | Verifier가 Builder 또는 Lead를 직접 지정 |
| 작업 문맥 | 역할/단계별 패킷, 각종 handoff | 원래 요청, 최근 역할 메시지, 직전 발신자, 사용자 피드백, 최신 파일 버전 |
| 실행 진행 | 운영 데몬이 단계 실행; 새 CLI는 기존에 한 역할씩 advance 필요 | 웹 tick과 같은 advance를 사용해 CLI run도 완료/대기까지 자동 진행 |
| 연구·장비 | 기존 검색/장비 실행 경로 있음 | 로컬 지식 연결은 있으나 새 런타임의 실제 웹 검색·장비 도구는 아직 없음 |
| 결과 | 기존 Verdict/run 중심 | 새 코어의 최종 응답·파일도 결과 화면에 연결하는 코드가 있음 |

주요 확인 위치:

- ../orchestrator/control.py — mission의 명시적 Offline 분기와 기존 사전 검사 경로.
- ../orchestrator/loop.py — 기존 prepared_plan 처리와 역할/단계 실행.
- ../orchestrator/contract_compiler.py — _compile_development도 장비 단계 계약을 컴파일·연결함.
- ../orchestrator/conversation_flow.py — 새 코어의 역할 전달·상태·결과 확인.
- ../orchestrator/conversation_service.py — 기존 소스 작업공간·지식·웹 제출 연결.
- ../orchestrator/conversation_codex.py — 새 코어의 실제 개발 도구 루프. 현재 offline 전용.

## 이번 변경

- 새 실행기를 추가하지 않고 ConversationFlow.run이 기존 advance를 반복한다.
  기존 턴 예산, 취소, 질문, 미확정 실행 중단을 그대로 존중한다.
- handoff는 직전 발신 역할과 이벤트를 가리킨다. 메시지 본문이나 Plan을 새 형식으로
  복사하지 않고 latest_messages에서 바로 읽는다. 실제 Codex 역할 지침에도 반영된다.
- 같은 경로의 산출물은 최근 전달된 해시 하나만 작업 문맥에 넣는다. 이전 버전과 실패 이유는
  원장과 최근 역할 메시지에 보존한다. 파일을 이전 버전으로 되돌려 최신 결과처럼 완료할 수 없다.
- 중단 상태를 나중에 조회해도 원장에 저장된 질문·중단 사유를 표시한다.
- CLI에 run / answer / feedback / cancel을 연결한다. 조회와 메시지 저장은 모델을 호출하지 않는다.
  Ctrl+C는 작업을 취소로 기록한다. 별도 CLI cancel은 락이 해제된 상태에서 사용하는 제어다.

## 제거할 문서 요구와 유지할 실행 확인

제거 대상:

- 개발을 시작하기 위한 Gate 번호, capability 강제 선택, 정확한 편집 파일 목록.
  새 코어에서는 이미 요구하지 않으므로 다시 도입하지 않는다.
- Lead에게 완성된 도구 인자 표나 하드웨어 YAML까지 작성하게 하는 요구.
- Builder가 코드를 준비한 뒤 이를 다시 prepared_plan으로 제출하고 컴파일받는 우회.
- 코드 수정이나 측정 방법 변경만으로 동일 장비의 권한을 처음부터 다시 받는 절차.
- 일반 오류를 에이전트가 처리하기 전에 플랫폼이 작업 전체 실패로 바꾸는 처리.

유지 대상은 실제 실행에 필요한 확인이다:

- 취소와 정지, 사용자 설정의 비용/시간 한도.
- 요청한 장비·연결인지, 사용할 전압/전류/종단 등 실제 입력이 허용되는지.
- 기록만 있고 결과가 없는 장비 동작을 재시작 후 무조건 반복하지 않는 것.
- 실행·측정 결과와 출처. 모델의 성공 선언만으로 실측 PASS를 만들지 않는 것.
- 원본 작업과 진행 중 작업을 섞지 않는 작업별 공간.

## 하드웨어를 같은 흐름에 넣은 구현

ConversationFlow에 hardware 플래그만 켜거나 기존 검사를 무시하지 않고, 장비 드라이버와
에이전트 사이에 호스트 소유 실행 연결부를 두었다.

1. 기존 장비 도구와 run 저장 코드를 재사용하는 실행 연결부가
   도구를 호출할 때 대상·연결·동작 인자를 받는다. 별도의 개발 계획 계약을 받지 않는다.
2. 현재 job에 저장된 사용자 요청 범위와 장비 설정을 호출 직전에 확인한다.
   과거 Campaign/계약 문서의 승인을 현재 권한으로 자동 가져오지 않는다.
3. 기존 드라이버가 요구하는 내부 설정 형식은 호스트 연결부가 구성한다.
   모델은 없는 전기적 수치나 배선을 채워 넣지 않는다. 누락되면 필요한 항목만 질문한다.
4. 실행 결과/오류/run 경로를 바로 Builder의 같은 대화 루프로 반환한다.
   실패가 곧 플랫폼 중단이 되지 않도록 하고, 결과 불명 상태는 명시적으로 중단한다.
5. Builder가 실제 결과를 Verifier에게 전달한다. 계약 파일 생성 자체를 진척이나 완료로 세지 않는다.
6. 검토 계약 하나와 장비가 식별된 신규 Hardware 요청의 라우팅을 전환했다.
   기존 작업과 식별이 불충분한 요청은 원래 실행기로 끝내며 과거 기록은 보존한다.

같은 연결부에 자료 검색을 별도 도구로 넣으면 Lead가 필요할 때만 조회할 수 있다.
지원하지 않는 연구/장비 기능을 사용 가능한 것처럼 모델에게 보여주지 않는다.

## 사용과 검증 범위

프로젝트 루트에서 새 오프라인 시나리오를 한 번에 실행한다. 실제 run은 모델 사용량을 소비한다.
아래 CLI는 빈 작업공간을 만들며 기존 소스가 필요한 작업은 웹의 소스 스냅샷 경로를 사용한다.

```powershell
py -3 -m QKD_PROJ.orchestrator.conversation_cli run --ledger QKD_PROJ/runs/conversation-dev/jobs.db --workspaces QKD_PROJ/runs/conversation-dev/workspaces --objective "덧셈 함수를 만들고 실행 결과를 저장해줘"
```

질문으로 멈춘 작업은 같은 ledger/workspaces/job으로 answer --message를 전달하고 run --job으로 이어간다.
status는 상태 확인, feedback은 진행 요구 보완, cancel은 작업 종료다. 완료/취소 작업을 자동으로 되살리지 않는다.

회귀 테스트는 tests/test_conversation_scenario.py 및 기존 conversation_flow/service/codex 묶음으로
검증한다. 실제 SQLite, 파일 수정, 역할 간 수정 요청, 웹 스냅샷 연결과 테스트 전송 계층을 사용한다.
새 기능의 실제 모델 전체 실행, 실물 장비, 운영 서비스 재시작·배포는 이 변경의 검증 결과와 구분한다.

검증 결과: 하드웨어 대화·승인·서비스·결과를 포함한 Python 관련 회귀 159개 중 **158 passed**,
5초 시작 제한 동시성 테스트 1개는 단독 재실행에서 통과했다. 웹 대화 피드 **28 passed**와
변경 Python 모듈 구문 검사도 통과했다. 실제 모델 전체 시나리오와 실물 장비 검증, 운영 데몬
재시작은 수행하지 않았다. 상세 구조는
[실행부 교체 4단계](execution-redesign-stage4.md)에 정리했다.
