# 자율 개발 모드 (`autonomous-v1`)

새 웹 mission에 적용합니다. 기존 원장·계약·취소된 job을 변환하거나 재실행하지 않습니다.

## 책임

- Lead: 시나리오와 기존 자료를 읽고 필요한 구조/도구/작업 순서를 선택합니다.
  보드 매칭 실패는 조사·코드 작성의 블로커가 아닙니다.
- Builder: job 작업공간에서 소스·패키지·테스트를 수정하고 실행 오류를 복구합니다.
  정확한 파일 목록과 재사용 전략은 강제하지 않습니다.
- Verifier: 결정론적 측정 결과를 변경하지 않고 원래 요구 전체의 충족 여부를
  별도로 확인합니다. 빌드 성공만으로 측정 요청을 완료하지 않습니다.
- 플랫폼: 격리 작업공간, 기록, 취소, 자원 예산과 실제 장비 권한을 관리합니다.

## 사라진 의무

일반 개발 step은 `codex_workspace`와 지시가 중심입니다. 기능 확인 기준은 자연어로
전달할 수 있고, 원장에 존재하지 않는 측정 필드를 만들어 채울 필요가 없습니다.
`contract_action`, `contract_spec`, `implementation.strategy`, capability 해시 선택,
정확한 `write_scope`와 매번 생성하던 개발 계약은 필요 없습니다.
조건의 수치와 근거는 여전히 요구사항에 맞아야 합니다.

검색 예산이 소진되어도 이미 확보한 사실로 계획할 수 있습니다. 웹 사용만 끕니다.
관련 없는 보드용 스킬을 전부 먼저 읽지 않습니다.
실행 중 관련 item 이벤트가 들어오면 idle timeout은 갱신하며 전체 턴 상한은
별도로 1시간(설정된 idle timeout이 더 크면 그 값)입니다. 모델 한도와 Campaign
상한이 무제한으로 바뀐 것은 아닙니다.

## 하드웨어

### 계획 전달과 장비 정보 정규화

autonomous-v1 Lead는 Plan 객체 하나를 직접 반환합니다. `handoff` 안에 JSON을
문자열로 다시 인코딩하지 않습니다. 동적인 도구 인자를 닫힌 런타임 스키마에 강제로
맞추지 않도록 이 Plan 턴에는 `outputSchema`를 보내지 않으며, 호스트의 JSON 파싱·
의미 검증·기존 형식 교정 경로는 유지합니다. 과거 객체/문자열 wrapper도 읽을 수
있습니다. 다른 역할과 discovery의 구조화 출력은 변경하지 않았습니다.

하드웨어 제안의 `configuration.device_map/scope/bbb`는 같은 이름의 내부 설정으로
옮깁니다. `scope.target`의 명시된 model/host/port와 `scope.channels`는 각각
`hardware_safety.devices`와 `scope_channels`에 반영합니다. 원문 설정은 보존하며
서로 다른 중복 값은 덮어쓰지 않습니다. 전압·종단·주소를 추측하거나 다른 장비를
승인하지 않습니다. 정규화 후 기존 SafetyGate와 실제 실행 시 위임 검사를 거칩니다.

### 새 시나리오가 최초 위임

Start의 Hardware 모드로 작업을 시작하면, 사용자 원문에서 요청한 장비와 현재 설정된
연결을 `Brief.resources.scenario_access`에 고정합니다. 기본 유효시간은 12시간,
자동 실행 상한은 job당 256회입니다. Lead는 필요한 작업을 직접 계획하고
Builder는 그 범위 안에서 통신·프로그램·측정·수정을 반복합니다. 별도 Campaign 버튼은
필수가 아닙니다. 전기적 안전 계약/드라이버 검사와 원장 기록은 그대로 사용합니다.

단순 비교/제외 언급은 위임으로 보지 않습니다. 알려진 장비 이름·프로파일 별칭과
실제 연결 설정으로 식별하며, 모호한 이름이나 미설정 새 장비는 사실 확인이 필요합니다.
임의 자연어의 모든 뉘앙스를 판별하거나 없는 드라이버를 자동 제공하는 기능은 아닙니다.
같은 장비에서 계약 파일·단계 이름이 달라져도 위임은 유지하지만, 다른 연결로 변경하면
자동 확대하지 않습니다. 명시적 Campaign 결정은 이후 우선하며 철회 뒤 자동 복원하지 않습니다.
취소/완료/기존 job에 소급 적용하지 않고, Review의 revise도 과거 위임을 복제하지 않습니다.
Offline 모드에는 이 위임이 적용되지 않습니다. 사람의 프로브/전원 연결 확인은 여전히 필요합니다.

### 호환 승인 및 실제 장비 검사

하드웨어 계약은 실제 장비 도구가 읽을 설정과 접근·안전 범위입니다.
Lead가 새 경계를 제안할 수 있지만 파일 설치 자체는 승인이 아닙니다.
플랫폼이 최초 시나리오 위임 또는 명시적 Campaign 범위와 대조합니다. 같은 경계에서
코드/검증 조건/단계 이름이 바뀌어도 계약 해시를 다시 만들지 않습니다.
Campaign은 현재 Plan의 계약을 읽습니다. 최초 preflight의 다른 계약으로 돌아가지 않습니다.

등록된 `measure_scope`는 기존 채널 수집 코드를 재사용하는 수동 입력 수집 도구입니다.
보드 프로파일 대신 실제 장비 모델/주소/포트, CH1~4 연결, 1 Mohm 종단,
채널별 최대 입력 절댓값과 출처, 중단 조건을 검토합니다. 장비 연결 설정도
Campaign에 해시로 묶습니다. 전원·발생기 출력·Flash·보드 핀 구동 권한은 없습니다.
측정 후 전압 검사는 과전압을 예방하는 물리적 보호기가 아니므로 올바른 프로브와
입력 연결은 사람이 확인해야 합니다. 이 도구는 50 ohm 설정을 지원한다고 주장하지 않습니다.

다른 장비 도구는 기존 실행 드라이버와 해당 하드웨어 검사를 유지합니다.
임의의 새 프로그래머/드라이버를 승인 없이 즉시 활성화하는 범용 장비 실행기는
구현하지 않았습니다. 복수 계약 또는 하나의 공유 계약을 단일 Campaign으로 검토할 수
있으며, 공유 계약도 도구별 장비 범위를 각각 표시합니다. 통합 계획은 Lead가 정하고,
플랫폼이 시나리오별 개발 순서나 별도 계약 파일 수를 강제하지 않습니다.

### 2026-09-09 계약과 통합 계획 단순화

- BBB+스코프 등 복합 문서의 스코프 검사는 해당 장비 모델/주소/포트와 채널 입력
  한계/종단/연결만 사용합니다. 스코프를 읽는 데 다른 보드의 전원 전류·핀 목록을
  요구하지 않습니다. 같은 문서의 BBB·프로그래밍 호출은 각 드라이버 검사를 받습니다.
- `CLK`, `SCLK`, `SPI.CLK` 같은 정해진 버스 표기 및 `1_Mohm`/high-Z 표기를
  정규화합니다. 다른 채널·물리적 핀·장비 주소를 임의로 같은 것으로 처리하지 않습니다.
- 승인된 일회 `program_cpld_sram` 실행은 런처가 고정한 도구/계약 해시를 사용합니다.
  오래된 YAML의 Approval 2 승인자/날짜/횟수 필드를 다시 요구하지 않습니다.
  기록에는 `bound_device_dispatch`를 남기고 존재하지 않는 사람 서명을 만들지 않습니다.
  후보 이미지·소스 해시, 파일 위치/크기, JTAG 대상, SRAM-only 검사는 유지합니다.
  바인딩 없는 독립 실행은 기존 명시적 후보 승인 조건을 유지합니다.
- 다음 Lead는 직전 통합 계획과 StepResult, Verifier 의견을 함께 받습니다.
  반복마다 전체 YAML/검색 자료를 복제하는 대신 컴파일된 계약 참조와 작업 순서를 전달합니다.
- 컴파일이 거부한 Plan은 `plan.validation_failed` 이벤트에 원문/해시/오류를 보존합니다.
  실행 가능한 Plan handoff로 기록하지 않으며 한 번의 교정은 검색 없이 해당 오류에 집중합니다.
  영구 오류·장비 결과 불명·권한 확대를 무제한 재시도로 감추지 않습니다.

이 변경은 여러 장비의 실시간 동기 실행기를 새로 만든 것이 아닙니다. 스코프 arm과
BBB 트리거를 동시에 제어해야 한다면 그 실행 경로와 실제 파형을 따로 검증해야 합니다.
기존 중단 job의 Plan/승인/장비 상태를 수정하거나 자동 재개하지 않습니다.

### 측정 코드 재사용과 승인 연결

`measure_scope` step의 선택적 `entrypoint: 경로/파일.py:함수`는 Builder가 수정한
job 작업공간의 측정 함수를 실행합니다. 별도 MCP 도구 등록은 필요 없습니다.
함수는 `(scope, params, gate)`를 받아 기존 `RecipeOutcome`을 반환합니다.
실행 직전 소스 해시를 고정하고 실제 실행한 파일을 run의 `executed_recipe.py`로 저장합니다.
기존 기본 수집기는 entrypoint를 지정하지 않았을 때만 사용합니다.

기존 active 스코프 전용 계약도 재사용합니다. 일반 수동 승인과 Campaign 모두
실제 계약·장비 연결 설정의 해시를 확인하며, 스코프 입력 수집에 CPLD 비트스트림을
요구하지 않습니다. 과거 계약에 없던 전압 상한을 검증된 값처럼 만들어 넣지 않습니다.
새 전기적 경계는 기존 검토 절차를 유지합니다. 제공된 스코프 인터페이스는 승인 채널의
1 Mohm 수집/설정을 검사하며 발생기 출력·리셋·다른 채널 접근은 허용하지 않습니다.
임의 Python의 모든 직접 통신을 OS 수준에서 격리한다는 보장은 아닙니다.

## 결과와 복구

코딩 결과는 공유 runs에 명령 출력과 변경 파일을 저장하고 작업공간은 보존합니다.
원본에 자동 복사하지 않습니다. 결과 카드의 작업공간 열기로 변경을 검토하고
Git diff/수동 병합을 진행합니다. 자동 병합 UI는 별도 기능입니다.

오프라인 Builder의 중단된 턴은 부분 실행 증거와 미완료 상태를 기록해
다음 계획에 전달합니다. 종료되지 않은 턴의 마지막 exit 0을 성공으로 보지 않습니다.
장비에 이미 어떤 효과가 있었는지 불명확한 중단은 무조건 재실행하지 않습니다.

마지막 셸 명령의 종료 코드를 작업 전체의 판정으로 사용하지 않습니다.
실제로 실행한 관련 테스트/빌드의 결과를 사용하고, 선택적 `verification_commands`
필드로 커스텀 검증 명령이나 command item ID를 지정할 수도 있습니다.
캐시 정리·ACL 작업의 실패는 별도 경고로 남깁니다. 검증이 없거나 마지막 편집보다
오래됐으면 `WARNING`이지 성공 근거가 아닙니다. 이 run 판정과 원래 기능의 충족
여부는 구별하며 최종 Verifier가 시나리오와 실제 자료를 비교합니다.
코드 준비가 실패하면 뒤의 장비 step으로 진행하지 않고 검토/재계획에 반환합니다.
Campaign 범위와 예산이 남아 있으면 사용을 마친 일회 승인은 다음 실행 때 자동 갱신합니다.

검증 횟수에 새로운 하드 리밋은 넣지 않았습니다. 관련 변경을 확인하는 작은 검증을
선택하고 변경이나 구체적 실패 근거 없이 전체 회귀를 반복하지 않도록 지시합니다.
`runs: []`로 반환해도 플랫폼이 실행 후 실제 run을 기록하므로 Builder가 원장 구현이나
run 형식을 찾아 읽을 필요가 없습니다. 다음 턴에는 반복되는 상세 audit/capability
목록 대신 선택된 작업·검증·실패 요약을 전달합니다.

참고용 재사용 카탈로그의 누락/해시 변경은 경고와 해당 추천의 제외로 처리합니다.
원본 카탈로그 해시나 과거 PASS 기록을 자동 수정하지 않으며 데몬 시작을 막지 않습니다.
실제 장비 승인에 묶인 해시 변경은 이와 달리 계속 재검토 대상입니다.

### 후속 흐름 점검

- 마지막으로 허용된 iteration도 실행합니다. 상한 2이면 첫 실패 뒤 두 번째
  Lead → Builder → Verifier가 실행되며, 두 번째 계획 직전에 중단하지 않습니다.
- 스코프 연결은 실제 사용하는 모델/IP/포트로 검토합니다. TCP 드라이버에서
  쓰지 않는 VISA `scope.resource` 문자열을 강제로 요구하지 않습니다.
- 하드웨어 설정 검증 오류는 `ContractCompileError`로 Lead의 계획 수정에
  전달합니다. 장비 접근 전에 수정하며, 설정이 잘못된 채 승인하지 않습니다.
- 신규 Verifier 응답은 `requirements_met`, `analysis`, `recommended_next_action`이
  중심입니다. 결정론적 표를 복사할 필요가 없으며, 형식 오류는 Verifier만 한 번
  교정합니다. Builder나 측정을 다시 실행하지 않습니다. 측정 판정은 모델이 바꿀 수 없습니다.
- 실제 MCP 완료 응답의 run과 동일 계약의 디스크 manifest가 일치하면 플랫폼이
  StepResult에 연결합니다. 모델이 run ID를 빠뜨린 것만으로 실제 측정을 잃지 않습니다.
  오래된 폴더를 검색하거나 mtime으로 run을 추측하지 않습니다. 불명확한 장비 중단을
  이 경로로 자동 재실행하지 않습니다.
- 잘못된 MCP 인자 이름/타입은 실제 호출 전에 돌려주므로 일회 장비 시도를 소모하지
  않습니다. 장비 실행을 시작한 후의 실패는 기존 시도 예산을 그대로 소모합니다.
- 파형 통계와 전기적 상한 검사에 쓰는 CH별 최솟값·최댓값, 종단 readback은
  실제 샘플/드라이버 값이 우선합니다. recipe의 같은 이름 값으로 덮어쓰지 않습니다.
- 단순 phase 조회에는 보드/지식 카탈로그 전체 재조회를 하지 않습니다.

이 점검은 공통 흐름과 현재 RTM3004 경로를 대상으로 합니다. 임의의 새 업로드
드라이버나 모든 vendor의 실물 검증을 완료했다는 뜻은 아닙니다.

#### 스코프 승인 재사용

- Inbox의 `이 단계 N회 승인`은 한 job의 한 단계에만 적용되며 취소 시 철회됩니다.
- Campaign 기본값 `authorization_scope: scenario`는 기존 시나리오 위임을 유지합니다.
- `scope_session`은 사용자가 Campaign 화면에서 명시적으로 선택하는 별도 위임입니다.
  유효시간 안에 다른 목표의 새 **hardware** job이 생겨도 동일 계약/역할/measure_scope/
  연결 파일 해시의 범위에서 자동 승인합니다. 승인 횟수는 모든 job이 공유합니다.
  보드 프로그램·전원·JTAG와 run-manifest 권한은 이 재사용 모드에 넣을 수 없습니다.
- 개별 job 취소는 그 job만 멈추고 그 단계 승인을 철회합니다. 스코프 세션 승인은
  Campaign의 `장비 승인 철회`로 별도 종료합니다. 취소된 job은 자동 부활하지 않습니다.
  실제 프로브 연결을 바꾸려면 기존 장비 승인을 먼저 철회하고 새 연결을 검토하세요.
- 승인 방식도 review digest와 YAML digest에 포함합니다. 기존 승인과 철회 기록을
  새 범위로 소급 해석하지 않습니다. 재시작 시 활성화 이벤트·만료·파일 해시를 재확인합니다.
- 활성화 이전에 만들어져 자체 만료일이 없는 요청도, 사용 시점에는 Campaign의
  만료일을 적용합니다. offline 데몬은 장비 승인을 복원하지 않습니다.
- 재사용 위임은 인증된 Campaign 화면에서 직접 승인합니다. 기존 일회용 원격 링크는
  한 job 전용이므로 재사용 옵션을 선택하면 링크 발급 버튼을 비활성화합니다.
  웹 화면 수정분은 build 완료 후 서버 재시작/새로고침, 원격 정적 배포는 별도로 필요합니다.

- 문법 검사·테스트 명령의 파일명은 실행 대상으로 오인하지 않습니다. 복합 셸과
  실제 프로그래머 명령은 별도로 확인합니다. 테스트/빌드 분류 자체는 장비 권한이 아닙니다.
- Campaign preview는 Plan의 모든 하드웨어 계약/해시를 각각 검토하고 한 번 승인합니다.
  웹과 휴대폰에도 모든 범위를 표시합니다. 실행 권한은 계약/역할/도구별로 분리됩니다.
- `hardware_boundaries: {name: configuration}`와 단계의 `contract: "$name"`으로 새
  제안을 명시적으로 연결합니다. 기존 `hardware_contract`는 `$hardware_boundary`만
  연결하며 다른 단계의 기존 계약을 덮어쓰지 않습니다.
- 연결 파일은 선택적으로 `device_map: relative/path.yaml`을 사용합니다. 보드 프로파일은
  필수가 아닙니다. 실제 장비 설정은 승인된 원본 root, 실행 함수는 job workspace에서 읽습니다.
- native JTAG/BBB/PRU 도구는 불필요한 profile/stage 검토를 요구하지 않습니다.
  BBB는 승인된 `bbb.target: {host, user, port}`와 실제 SSH 대상이 같아야 합니다.
  비밀번호는 계약/화면에 저장하지 않습니다. JTAG scan은 전압/핀을 검사하지만 전원
  공급을 하지 않으므로 무관한 공급 전류 한도를 요구하지 않습니다.
- 비스코프 도구에도 `entrypoint: file.py:function`을 사용할 수 있습니다. 함수는
  `(device, params)`를 받아 `device.execute(**tool_arguments)`로 승인된 동작을 한 번
  실행합니다. 스코프 함수는 기존 `(scope, params, gate)` API를 유지합니다. 새 도구
  등록 없이 구현 코드를 바꿀 수 있으며, 실제 드라이버 결과·실패·실행 소스를 보존합니다.
- 이 인터페이스는 기존 장비 드라이버 위의 확장점입니다. 임의 SSH/프로그래머 실행권이나
  없는 vendor 드라이버를 자동으로 제공하지 않습니다. 기존 BBB script allowlist,
  PRU 배포 절차, CPLD SRAM/XCF 검사는 드라이버에 남습니다. 새로운 프로토콜/업로드 방식은
  해당 드라이버의 별도 구현 및 검증이 필요합니다.
- 완료된 MCP run이 확실하면 마지막 JSON 응답 오류만 복구하고 장비를 반복하지 않습니다.
  미완료 장비 호출/물리 상태 불명은 자동 재실행하지 않습니다. 오프라인 코드/경로 오류는
  실제 실패 run과 함께 재계획으로 전달합니다. 승인 요청은 완료 StepResult로 저장하지 않습니다.
