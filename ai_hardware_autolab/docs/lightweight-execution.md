# 짧은 실행과 새 보드 개발

보드 종류나 시나리오 키워드로 실행 순서를 고정하지 않는다. Lead가 현재 요청에
필요한 일을 결정하고, 이미 인자가 확정된 호출만 플랫폼이 직접 수행한다.

## 기존 기능으로 충분할 때

`Lead → Builder 실행 슬롯(모델 호출 없이 도구 1회) → Verifier → 완료/재계획`.
Plan의 step에 선택적으로 다음을 쓴다. 사용자가 이 JSON을 작성할 필요는 없다.

```json
{
  "id": "identify-bbb",
  "agent": "builder",
  "tool": "run_bbb",
  "execution": "direct",
  "tool_args": {"identity_only": true},
  "touches_hardware": true,
  "contract": "$bbb-identity",
  "instructions": "현재 BBB에 SSH 로그인하여 모델과 커널을 확인한다.",
  "acceptance_criteria": ["요청한 BBB의 실제 모델과 커널을 보고한다."]
}
```

`tool_args`에는 `contract`/`record_name`을 넣지 않는다. 호스트가 Plan의 계약을
사용한다. 직접 실행도 원장의 승인 사용을 먼저 기록하고, 호스트 계약/장비 맵과
해시를 검사한 뒤 동일한 MCP registry handler를 호출한다. 워크스페이스에 복사된
안전/통신 모듈을 신뢰하지 않는다. 결과는 해당 호출이 만든 manifest와 연결한다.

`runtime.platform/tool/started`와 `runtime.platform/tool/completed` 이벤트는
`execution: direct`, `model_invoked: false`를 명시한다. Codex 모델이 말했다고
가장하지 않는다. 일반 driver FAIL은 다음 계획에 실제 실패 원인을 전달한다.
결과가 기록되지 않은 예외는 장비 상태 확인 전 재실행하지 않는다. 취소는 추가
실행을 막지만 이미 장비가 받은 동작을 되돌리지는 않으며, 진행 중 I/O는 기존
드라이버 timeout까지 걸릴 수 있다.

## 접속 확인에 필요한 최소 동작

| 도구 인자 | 계약 allowed_operations | 실제 동작 |
| --- | --- | --- |
| run_bbb, identity_only=true | bbb_identify | SSH 로그인, 모델·커널 조회 |
| measure_scope, identity_only=true | scope_identify | *IDN?, *OPT? 조회 |

두 경우 모두 해당 장비의 확인된 연결 정보는 필요하다. BBB 인증은 기존 로컬
환경/Windows Credential Manager에서 읽으며 비밀번호를 Plan에 넣지 않는다.
식별 전용 scope 계약은 채널이나 입력 전압이 필요하지 않다. GPIO 구동, 프로그램,
전원 변경, 파형 측정의 권한으로 바뀌지는 않는다. 실패 시에도 scope STOP이나
출력 변경을 보내지 않는다. 식별 성공은 기능 검증 성공과 다르다.

## 진단 완료와 장비 성공은 별개

"연결 상태만 확인하고 안 되면 실패 원인을 보고해줘"라면 Lead는 식별 전용 단계에
`completion: diagnostic_report`를 선택한다. 사용자가 별도 YAML을 작성할 필요는 없다.
기본 판정 조건은 `measurements.diagnostic_complete == true`이며, 실제 호출에 연결된
run의 식별 결과 또는 실패 단계·오류가 있어야 한다. BBB PASS / scope FAIL이어도
Verifier가 원래 진단 요청을 충족했다고 확인하면 한 iteration에서 끝낼 수 있다.
장비 FAIL은 manifest/StepResult와 결과 카드에 그대로 남는다. 이는 연결 복구나
파형 목표 달성을 의미하지 않는다. 명시적인 성공 조건은 자동으로 삭제하지 않는다.

- 스코프: TCP 연결 / `*IDN?` / 모델 확인 / `*OPT?` 실패를 구분한다.
- BBB: 연결 설정 / SSH 연결·인증 / 모델·커널 조회를 구분한다.
  SSH 연결과 인증의 더 세밀한 원인은 실제 오류에서 확인하며 추측하지 않는다.
- 승인 거부, 로컬 인증 정보 누락, 내부 코드 오류, 결과 기록 누락은 진단 완료가 아니다.
- 기본 도구가 원인과 부분 응답을 기록하므로, 실패 단계만 알아내려고 새 드라이버를
  작성하거나 같은 연결을 반복할 필요가 없다.

작업공간에서 **호스트가 사용하는 드라이버**를 수정해도 설치된 도구가 바뀌지는 않는다.
이전 StepResult의 변경 감사에 관련 경로가 있으면 다음 장비 단계 전에 작업공간과
호스트 파일 해시를 비교한다. 다르면 `platform_deployment`로 멈추고 재시험하지 않는다.
일반 레시피·사용자 코드·테스트 편집은 이 검사 대상이 아니다. 이 검사는 별도 배포나
메모리에 로드된 코드의 교체를 수행하지 않는다. 반영할 코드는 사람이 검토하고,
반영 후 관련 프로세스를 재시작해야 한다.

## 중단과 해당 단계 재개

미해결 blocked StepResult는 job 행이 running이어도 다음 장비 단계로 넘기지 않는다.
하드웨어 단계는 호출 전에 `step.dispatch.started`를 원장에 기록한다. 재시작 후 이 기록에
대응하는 StepResult가 없으면 장비 동작의 결과를 추측하거나 재실행하지 않는다.

Agents의 **원인 해결 후 재개**는 장비에 접촉하지 않았다고 기록된
`platform_deployment` 중단에만 적용된다. 수정본을 검토해 원본에 반영하거나 불필요한
작업공간 수정을 되돌리고, 원본이 변경됐으면 데몬/관련 도구 프로세스를 재시작한다.
해결 내용을 적고 재개하면 서버가 해당 job 작업공간과 현재 소스 상태를 다시 확인한다.
피드백 전송만으로 중단을 해제하지 않는다. 취소/완료 job, 예산 소진, 미확정 장비 결과는
이 버튼으로 재개할 수 없으며, 이 기능이 장비 권한이나 예산을 확대하지도 않는다.

원장은 기존 handoff를 수정하지 않는다. 하나의 트랜잭션으로 새 iteration, 같은 Plan,
완료 단계의 `reused_from` 참조를 기록하고 미실행 단계만 남긴다. 이전 run을 새 측정으로
가장하지 않으며 재사용 이벤트는 사용자 피드백 전달로 계산하지 않는다. 중복 클릭과
트랜잭션 중 크래시는 부분적인 재개를 남기지 않는다. 재개도 iteration 한도를 소비한다.

장비 도구의 호출 직전에도 해당 턴 시작 이후 호스트/작업공간 드라이버 소스 변경을
확인한다. 코드 반영이나 프로세스 재시작을 자동 실행하지 않는다. 이 소스 검사는
프로세스/턴 시작 시 파일 기준이며 악성 코드에 대한 OS 격리나 메모리 코드 증명은 아니다.

## 새로운 보드나 구현이 필요한 경우

`execution`을 생략하거나 `agent`로 두면 기존 Builder 모델 경로를 사용한다.
Lead는 기존 지식으로 해결되지 않은 항목을 공식 데이터시트·매뉴얼에서 조사하고,
새 보드의 핀·인터페이스·제약을 근거로 구조를 설계한다. Builder는 작업공간에서
코드/레시피와 필요한 테스트를 작성한다. 자료 조사는 금지하지 않으며, 변경한
기능과 무관한 회귀 테스트나 반복 검색을 기본 단계로 만들지 않는다.

일반 개발에는 새 계약/보드 프로파일을 강제하지 않는다. 실제 장비 연결은 검토된
전송 경로와 해당 장비 권한이 필요하다. 새 vendor/protocol 드라이버가 필요한 경우
구현·검증 작업이 남아 있으며 임의 shell에 장비 접근을 개방하는 경로는 아니다.

## 검증 범위

`tests/test_lightweight_execution.py`는 가짜 SSH/SCPI와 실제 원장/승인/실행기/
판정기를 연결한다. 한 iteration, 장비별 별도 run, 추가 Builder 모델 호출 없음,
허용 범위 유지, 신규 보드 개발 계획 유지, 피드백 전달을 검사한다.
라이브 모델이나 장비를 호출하지 않으므로 실제 시간/토큰 절감 수치는 주장하지 않는다.
프런트 소스는 바꾸지 않았다. 데몬 재시작 후 새 요청으로 실물 검증한다.
`tests/test_diagnostic_execution.py`는 단계별 실패, 보고 완료/장비 FAIL 분리,
Verifier의 독립적인 거절, 미적용 드라이버 재실행 방지를 오프라인으로 검사한다.
